# 新项目的目录与文档设计

一套与语言、框架无关的约定。目标是**三个月后还有人（和 AI）能快速找到需要的东西**，而不是把仓库塞满没人读的文档。

配套模板在 `templates/`，用到时复制过去填，不要凭记忆重写。被 `/project-layout` 调用时，按「六、初始化清单」逐步走。

## 零、规则速查（写 docs 前对照）

会话里要往 `docs/` 写任何文件，先看这一节，不用读全文。没有自动校验——这些是约定，不是闸门；项目要偏离就写进该仓库 CLAUDE.md 的「文档规则」节，以那里为准。

| 位置 | 文件名 | 头部 |
|---|---|---|
| `docs/README.md` | 固定 | 通用头部 |
| `docs/research/` | `YYYY-MM-DD-<slug>.md`，**必须带日期** | 通用头部 |
| `docs/design/` | `<slug>.md`，**不带日期**，不分子目录 | 通用头部 |
| `docs/adr/` | `NNNN-<slug>.md`，四位编号 | ADR 头部 |
| `docs/guides/` | `<slug>.md`，不带日期 | 通用头部 |
| `docs/assets/` | 任意（图片等附件） | 无 |
| `docs/` 根的其它文件、其它子目录 | 不放 | |

- 文件名一律小写连字符 `[a-z0-9-]`，扩展名 `.md`。
- **通用头部**：第 1 行 `> 状态：<草案|评审中|已定稿|已实现|活文档>`；前 6 行内有 `> 摘要：` 和 `> 何时读：`。
- **ADR 头部**：第 1 行 `> 状态：<提议中|已接受|已取代>`；前 6 行内有 `> 日期：` 和 `> 摘要：`。
- 状态词后可加括号补充（`已接受（第 2 节 2026-08-01 修订）`），但开头必须是固定词。
- 实施计划、排查记录、checklist 写 `.scratch/`（已在 `.gitignore`）；进度看板不进仓库，用 GitLab issue。
- 需求变更**必须**记：没推翻决策的写进 design 文档「变更记录」表，推翻了的写新 ADR。进度可以丢，变更原因不能丢。
- `docs/superpowers/` 是冻结的旧快照，**不新增**文件。

拿不准放哪：不是随手起个目录，是先想清楚**这东西该不该进 docs**（见「什么不进 docs」）。项目级偏离（跨仓契约 `docs/api.md`、monorepo 的 `design/modules/`、生成的协议文档）写进该仓库 CLAUDE.md「文档规则」节，一行说清是什么、为什么——由用户拍板，AI 不自行开例外。

## 一、目录设计

### 三条硬原则

**1. 用到才建，不预先铺空壳。**

约定是「东西该放哪」，不是「现在就要造出这些目录」。空目录传递假信息 —— 让人以为那里有内容、以为项目已经分了这么多层。第一天只建真正有文件的目录。

**2. 纯逻辑与 I/O 分离。**

核心业务逻辑不直接依赖数据库、HTTP 客户端、SDK、引擎、文件系统。外部能力通过接口注入，实现放在适配层。

这条不是为了架构好看，是为了**测试能脱离外部依赖跑**。判断标准很具体：核心逻辑的单元测试，能不能在没有数据库、没有网络、没有真实 SDK 的机器上跑通？不能，就说明这条没做到。

代价是多一层接口定义。收益是核心逻辑可以被真正测试、外部依赖可以被替换。规模再小的项目，只要核心逻辑有分支判断，这个代价就是划算的。

**3. 探路代码与生产代码物理隔离。**

验证想法的代码放 `spike/`，不进 `src/`、`apps/`、`packages/`。spike 允许脏、允许硬编码、允许不写测试 —— 前提是它待在自己的目录里，不被生产代码 import。

验证完了，要么把结论提炼进正式实现（spike 代码删掉或留作参考），要么记进 research 文档。不要让 spike 悄悄变成生产依赖。

### 两种形态

**单服务项目** —— 直接分层，不套 `apps/`：

```
src/            源码
tests/
docs/
scripts/        构建、部署、排障
spike/          探路代码（用到才建）
.scratch/       跨会话的临时产物：实施计划、排查记录、checklist（git 忽略）
```

**monorepo** —— 按**部署单元**和**语言边界**划分，不按技术类型：

```
apps/           可独立部署的服务，一个目录一个部署单元
packages/       被 apps 复用的库；纯逻辑包在这里，零外部依赖
docs/
scripts/
spike/
.scratch/
```

划分依据只有两条：**能不能独立部署**、**是不是同一种语言/工具链**。跨语言的部分不要硬塞进同一个包管理器的 workspace —— 各用各的工具链，用容器编排层拼起来。

包内部怎么分层（按功能分还是按技术类型分）是包自己的事，不在这套约定的管辖范围。小包别分层。

## 二、文档体系

### 分层：渐进式披露

文档的敌人是「要读完才知道跟我无关」。分四层，每层都能让人在读下一层之前判断要不要继续：

| 层 | 是什么 | 内容 |
|---|---|---|
| **L0 常驻** | `CLAUDE.md` | 铁律 + 约定摘要 + 指针。每次会话都加载，必须最精炼 |
| **L1 入口** | `docs/README.md`（地图） | 导航，先读这层再决定深入 |
| **L2 主题** | `docs/design/`、`docs/research/`、`docs/adr/`、`docs/guides/` | 自包含，顶部有头部 |
| **L3 细节** | L2 文档内部的决策表、测试计划、实现记录 | 需要时才展开 |

`docs/README.md` 是文档地图，第一节必须是「要做什么 → 读哪个」的路由表。它的价值在于让人**不读其他文档就能判断该读哪个**。

### 统一头部（所有 docs 文档必须有）

引用块放在文件**最前面**，第 1 行就是 `> 状态：`；`# 标题` 在引用块之后。这个顺序是固定的 —— 头部在第 1 行，`head -4` 就能判断相关性，也不跟工具的 frontmatter 解析打架：

```markdown
> 状态：草案 | 评审中 | 已定稿 | 已实现 | 活文档
> 摘要：一句话说清本文是什么（扫这句就能决定要不要读全文）
> 何时读：什么任务该打开我
> 依赖：相关文档链接，或「无」

# 标题
```

ADR 用自己的一套：`> 状态：提议中 | 已接受 | 已取代`，加 `> 日期：`（见模板）。

**「摘要」和「何时读」是这套体系里最有价值的两行。** 它们让人和 AI 扫头部就能判断相关性，不必把全文灌进上下文。写文档时这两行最容易敷衍，但它们决定了文档会不会被读到。

「状态」不是装饰 —— 看到「草案」就知道结论可能变，看到「已实现」就知道可以照着做。状态过期比没有状态更糟，改了实现记得回来改状态。状态词用上面那几个固定词，要补充说明写在后面的括号里。

### 分类与命名

```
docs/
├─ README.md          文档地图（L1 入口，必须有；根目录只允许这一个文件）
├─ research/          调研、选型对比 —— YYYY-MM-DD-<topic>.md
├─ design/            功能与模块设计 —— <topic>.md，一个功能一个文件
├─ adr/               关键决策 —— NNNN-<slug>.md，四位数字递增
├─ guides/            操作手册：部署、发版、CI、分支规则、排障 —— <topic>.md
└─ assets/            截图等附件，正文不直接放图
```

**文件名一律小写连字符**：`resume-review-design.md`，不要 `RESUME_REVIEW_DESIGN.md`。

**research 带日期前缀，design / guides 不带。** 调研是某个时间点的市场/技术快照，日期是它的一部分 —— 半年后看到 `2026-07-28-` 就知道该重新调研了。设计文档和操作手册是活的，会随实现更新，加日期反而暗示它过期了。

**「方案」也是 design 文档，同样不带日期。** 文件名是主题的身份，不是时间戳：方案没定就写 `状态：草案`，定了改 `已定稿`，做完改 `已实现`；改版就在同一个文件上改，旧版本在 git 历史里；被否决就删文件，否决理由进 ADR。给方案加日期、加 `-proposal`、`-v2` 后缀，都是在用文件名替代状态字段，最后 design/ 会堆满一次性文件。

**guides 是「怎么操作」，design 是「为什么这样设计」。** 部署步骤、CI 怎么触发、分支怎么切、出了问题查哪里 —— 进 guides；一个模块的边界、接口、取舍 —— 进 design。

**monorepo 里，只服务于单个包的模块设计文档随包放**（`packages/<pkg>/docs/modules/<module>.md`），不要集中到根 `docs/`。理由：删包的时候文档跟着删，不会留下孤儿文档。

### ADR：关键决策记录

一条决策一个文件，`NNNN-<slug>.md`，编号只增不减。

**记什么**：为什么这么选、否决了什么、否决的理由。**不记**实现细节 —— 那是 design 文档的事。

**ADR 不可删除、不可覆盖。** 决策变了就写新 ADR，并在**旧 ADR 顶部加一行指向新 ADR 的更新说明**：

```markdown
> **更新（[ADR-0005](0005-xxx.md), 2026-07-28）**：本文决策 4 已被 ADR-0005 修正 —— <一句话说清改了什么>。其余决策不变。
```

这样保留了决策的演化轨迹。直接改旧 ADR 会让「当初为什么那么想」永久丢失，而那恰恰是半年后最需要的信息 —— 没有它，同一个坑会被重新踩一遍。

**ADR 的一个隐藏价值**：它记录了**被否决的方案**。人们通常只记住选了什么，而「我们认真考虑过 X，因为 Y 没选」能挡住后来者反复提同一个建议。

编号按仓库独立。跨仓引用写 `<仓名>#ADR-NNNN`，别让读者猜是哪个仓的编号。

### 什么不进 docs

**一次性的东西不进。** 实施计划、修复计划、临时排查记录、迁移 checklist、阶段性总结 —— 写 `.scratch/`（git 忽略）。`docs/` 只放「三个月后还有人会读」的东西。

`.scratch/` 的逻辑：这些产物只对**当前分支**有意义。分支没做完不允许合并，合完 worktree 一删它们就跟着消失，正好。跨会话续做靠它在磁盘上，**不靠 Claude 的 scratchpad**（那个是会话级的，会话一结束就没了，AI 才会另起 `docs/plans/` 之类的目录）。写之前确认 `.gitignore` 里有 `.scratch/`。

判断方法：问自己「这个任务结束后，还有人会打开它吗？」答案是否，就不进 docs。

**进度看板不进仓库。** 用 GitLab issue（`glab issue`）跟踪进度和阻塞；仓库里的 `progress.md` 从来没有一份是不过期的。

**但需求变更必须进仓库。** 进度是「做到哪了」，可以丢；变更是「为什么改、当时踩了什么」，丢了同一个坑就会重踩。两个落点：
- 改了做法但没推翻决策 → 对应 design 文档的「变更记录」表（日期、改了什么、当时遇到了什么）。
- 推翻了原决策 → 写新 ADR，旧 ADR 顶部加更新行；ADR 的「否决理由」就是给未来的人挡坑用的。

`.scratch/` 里的计划因为需求变了要改时，先把「为什么变」写进上面两处，再动计划 —— 计划会随分支消失，原因不能跟着消失。

**不手写 API 文档和数据库表结构文档。** API 看框架自动生成的 OpenAPI，表结构看模型定义或迁移文件。手写副本必然过期，而**过期的文档比没有文档更坏** —— 它会让人做出错误决定，且错得很自信。

## 三、CLAUDE.md 写什么

CLAUDE.md 是 L0，每次会话常驻，**每多一行都在消耗每次对话的上下文预算**。它的定位是「铁律 + 指针」，不是项目说明书。

**该写**：
- 项目一句话定位、当前阶段
- 核心铁律（违反了就是 bug 的那种约定，不是最佳实践建议）
- 目录结构与规则
- 开发约定（分支、构建、测试怎么跑）
- 业务红线（合规要求、安全约束）
- 明确的「不要做的事」
- **指向详细文档的指针**，而不是详细内容本身

**不该写**：
- 决策的完整论证 → 放 ADR，CLAUDE.md 只留结论和链接
- API 清单、表结构 → 看代码
- 教程性内容、背景介绍 → 放 README.md（给人看的）或 design 文档
- 还没定的东西 → 定了再写，别写「待定」

一条实用检验：**CLAUDE.md 里的每一句话，如果 AI 违反了，是不是真的会造成问题？** 不是，就该删掉或移走。超过百行，多半有东西该下沉到 `docs/`。

**不要把本 skill 的内容抄进 CLAUDE.md。** 通用约定放这里按需加载，CLAUDE.md 只留一行指针 + 项目特有的部分。抄一遍等于每次会话都付一遍上下文成本，而且两处会各自漂移。

**那行指针必须保留，而且要带文件路径**：本 skill 是手动触发的，会话里的 AI 调不到 `Skill(project-layout)`，只能 `Read` 文件。模板里已经写好，别删。

`README.md` 和 `CLAUDE.md` 的分工：README 给人看（这是什么、怎么跑起来），CLAUDE.md 给 AI 看（约定和红线）。内容会有重叠，不必强行去重。

## 四、反模式

| 反模式 | 为什么坏 |
|---|---|
| 预先建满空目录 | 传递假信息，让人以为项目已经这么分层了 |
| `docs/` 平铺几十个大写下划线文件 | 找不到东西，`FIX_PLAN_*` 之类的一次性产物永久占位 |
| design 文件名带日期 / `-proposal` / `-v2` | 用文件名替代状态字段，design/ 变成一次性文件堆 |
| 实施计划进 `docs/`（`docs/plans/` 之类） | 做完就没人读，永久占位；该进 `.scratch/` |
| 操作手册散在 `docs/` 根 | 根目录变杂物间；该进 `guides/` |
| 手写 API / 表结构文档 | 必然与代码脱节，过期文档比没文档更坏 |
| 文档没有头部 / 头部不在第 1 行 | 每次都要读全文才知道跟自己有没有关系 |
| 决策论证写进 CLAUDE.md | 挤占每次会话的上下文预算 |
| 改旧 ADR 而非写新 ADR | 丢失决策演化轨迹，同一个坑会重踩 |
| spike 代码被生产代码 import | 脏代码悄悄变成生产依赖 |
| 文档状态永远停在「草案」 | 状态失去信号价值，等于没有 |

## 五、模板

`templates/` 下有可直接复制的骨架：

| 文件 | 复制到 | 何时用 |
|---|---|---|
| `claude-md.tpl.md` | `CLAUDE.md` | 建仓库时 |
| `docs-readme.tpl.md` | `docs/README.md` | 建仓库时（文档地图必须有） |
| `adr.tpl.md` | `docs/adr/NNNN-<slug>.md` | 有关键决策要记时 |
| `design-module.tpl.md` | `docs/design/<topic>.md` | 设计某个功能/模块时 |

建仓库时只需要前两个，外加 `.gitignore` 里一行 `.scratch/`。其余用到才复制 —— 这正是「用到才建」在文档上的体现。

## 六、初始化清单（`/project-layout` 执行这个）

在目标仓库自己的窗口里跑，一步一步来，每步只补缺、不动已有的东西。`T=~/.claude/skills/project-layout/templates`。

1. **看现状**：`ls`、`git status`、有没有 `CLAUDE.md` / `docs/` / `.gitignore`。老仓库（已有 docs）和新仓库走同一套，差别只在第 6 步。
2. **定形态**：单服务还是 monorepo（见「一、两种形态」）。只建现在就有文件要放的目录，空壳不建。
3. **建 CLAUDE.md**：`cp $T/claude-md.tpl.md CLAUDE.md`，填占位符；「文档规则」那段指针不能删。已有 CLAUDE.md 的只补那段指针 + `.scratch/` 规则，别重写。
4. **建文档地图**：`mkdir -p docs && cp $T/docs-readme.tpl.md docs/README.md`，路由表只写真实存在的文档。
5. **`.gitignore` 加 `.scratch/`**（一行）。
6. **老仓库对照第零节过一遍**：把偏离项（根目录散文件、design 带日期、没头部、`docs/plans/` 之类）列给用户，**逐条**决定是改（改名 / 搬目录 / 补头部）还是保留并写进 CLAUDE.md「文档规则」。不自行决定，也不为了"合规"批量搬家。`docs/superpowers/` 是冻结快照，不动。
7. **提交**：一笔 `chore(layout): 接入 project-layout 约定`，内容就是上面新增/改动的文件。

做完把两件事报给用户：建了哪些文件、第 6 步里等用户拍板的项。
